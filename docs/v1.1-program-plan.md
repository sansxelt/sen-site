# Vraelis V1.1 Platform Expansion — Program Plan (first deliverable, 2026-07-12)

Spec: the founder's V1.1 program message (23 sections). Principle: Vraelis owns the customer experience;
one deep system: context -> deployment identity -> requirements -> flows -> evidence -> issue lineage ->
repair verification -> release decisions -> release intelligence. Phase 0 (pricing cutover) PASSED.

## 1. Current architecture audit
- Hosts: vraelis.com (marketing+auth) / app.vraelis.com (product) via host-based proxy (lib/app-routes.ts,
  proxy.ts); session cookie .vraelis.com; NextAuth redirect callback already family-allowlisted.
- Data plane: service-role Supabase, user_id = lowercased email on every row; RLS deny-anon backstop.
- Execution: Railway worker (Dockerfile, /health, lease queue v_preflight_claim, reaper), Browserbase via
  native-fetch REST, fail-closed provider guard (no fake browser in production).
- Billing: dual-unit ledger (credit legacy / cent live), flow-unit entitlement metering (anchor monthly
  windows), _v1 Stripe subscriptions, PAYG cents holds, all behind VRAELIS_PASS_PRICING=1 (now ON).
- Context: v_applications (environment/context jsonb/test_boundaries), v_app_connections (manual metadata
  + AES-256-GCM sealed test accounts), connect workspace with progressive disclosure.
- Decisions: coverage-aware decideRun (ready/needs_review/blocked/repair_verified), pickHealthRun
  (full-coverage rule), issue reconciliation planReconcile, linked reruns w/ parent provenance.
- Verification culture: 12 suites, ~600 checks, all green; static+pure+spy test patterns established.

## 7. Payment flow design
Native review screen (plan, exact amount, interval, entitlements, renewal + cancellation behavior) ->
server-created Checkout Session (idempotency key = uuid stored in v_events; success_url
app.vraelis.com/billing/success?session_id=..., cancel_url /billing/cancelled) -> webhook remains the
ONLY activation authority (already true) -> success page POLLS /api/v/me until plan_v1 appears (pattern
already exists on credits page) -> duplicate-checkout guard: refuse a new session while one is pending
for the same plan (session id logged in v_events). Native billing history: list Stripe invoices for the
customer server-side, render natively, hosted-invoice link as fallback detail.

## 8. OAuth flow design (GitHub first; template for the rest)
GitHub App (not OAuth app): installation flow from /applications/[id]/settings/connections with signed
state = HMAC(app_id, user, application_id, nonce, exp) stored server-side; callback verifies state,
exchanges code server-only, stores installation_id + encrypted token via secret vault, imports README/
metadata into a context snapshot draft, returns to .../settings/connections?connected=github. PKCE where
supported (GitHub Apps use client secret server-side; Supabase/Vercel OAuth get PKCE). Tokens never in
the browser. Idempotent by nonce; replay = "connection already completed" screen.

## 10. Secret + boundary threat model (delta on existing)
Assets: sealed test accounts (existing), provider OAuth tokens (new, same vault), webhook signing
secrets (env), avatar bucket (existing). Threats addressed: worker plaintext exposure (decrypt-at-use,
scrub after, never in steps/screenshots/logs - workstream W1 adds redaction of typed credential values
from step detail + skips screenshot on auth steps), boundary bypass (worker evaluates boundaries before
EVERY action, fail-closed, blocked-by-policy result never bills or opens app issues), webhook forgery
(signature verification + delivery-id dedupe), OAuth state replay (nonce single-use), token theft from
DB (sealed via vault; operator views masked). Railway needs VRAELIS_SECRET_KEY (operator action) for
worker decryption.

## 12. Worker changes
(a) Test-account sign-in: new semantic step actions sign_in_as/verify_authenticated/verify_unauthorized/
sign_out; claim() resolves role -> connection id; openTestAccount at execution moment; fill password via
provider without echo (step detail records "entered credentials for <role>" only); screenshots skipped
on password-entry steps; session isolation per role via new_context. (b) Boundary enforcement: claim
carries test_boundaries; pre-action gate (origin allowlist from allowed_domains, action class vs
permits); violation -> flow result blocked_by_policy (new state, never an app issue, refund if nothing
ran). (c) Deployment identity: run records deployment_id snapshot. (d) Redaction hardening for network
headers/console already sanitized - extend to typed values.

## 13. Contract-generation changes

generated requirement carries source: prompt|summary|prd|readme|connection:<kind>|manual|inference,
rendered as provenance chips; inference clearly labeled; approval flow unchanged (user approves before
execution).
