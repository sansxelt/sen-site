# v0.1.9 — Stripe products, env vars, webhooks, and the credits ledger

Replaces `v0.1.8-stripe-setup.md` for the operator (you). v0.1.9
collapses the per-feature one-time SKUs (voice_minute_pack /
image_credit_pack / copilot_time_pack) and the unlimited-feature
recurring packs (voice_pack / image_pack) into a single **flexible
credit ledger**. You only have to maintain four monetization SKUs in
Stripe now; everything else routes through `Buy credits`.

## 2. Credits — how the new flow works

1. User opens **Billing → Credits** in the desktop app and clicks
   **Buy credits**.
2. Modal pops with five preset buttons ($5/$10/$25/$50/$100) and a
   slider covering $1–$500.
3. App POSTs `{ amount_dollars }` to `/api/desktop/billing/credits`.
   Server creates a Stripe `PaymentIntent` for that amount in cents
   with `metadata = { kind: "credits", email, dollars }` and returns
   the `client_secret`.
4. Stripe Elements collects the card; `payment_intent.succeeded`
   webhook fires.
5. Webhook handler (`app/api/stripe/webhook/route.ts`) sees
   `metadata.kind === "credits"`, calls
   `addCredits(email, dollars * 100, "purchase", payment_intent_id)`.
6. `credit_transactions.id = "purchase:<payment_intent_id>"` is the
   primary key, so a re-delivered webhook is a no-op (unique-violation
   swallowed).

### Burn rates (`CREDIT_COSTS` in `lib/credits.ts`)

| Feature       | Credits per call |
| ------------- | ---------------- |
| `chat`        | 1                |
| `image`       | 5                |
| `voice_minute`| 2                |
| `copilot`     | 1                |

Gating layer (`lib/plan-limits.ts`) calls `consumeCreditFor(email,
kind)` whenever a plan limit blocks a request. If the user has enough
credits the request is allowed and the balance is debited; otherwise
the original blocked decision stands.

## 5. SQL migrations

Run **both** migration files against production Supabase. v0.1.8's
`boost_credits` table stays in service for `session_boost` /
`weekly_boost` (those still mint per-purchase rows). v0.1.9 adds
`user_credits` + `credit_transactions` for the new ledger.

- `docs/v0.1.8-boost-credits.sql` — keep applied.
- `docs/v0.1.9-credits.sql` — apply for v0.1.9.

Schema summary for the new tables:

```
user_credits (
  email      text pk,
  balance    integer not null default 0,
  updated_at timestamptz default now()
)

credit_transactions (
  id         text pk,            -- "purchase:<pi_...>", "consume:<...>"
  email      text not null,
  delta      integer not null,   -- positive = topup, negative = burn
  source     text not null,      -- 'purchase' | 'consume' | 'refund'
  ref_id     text,
  created_at timestamptz default now()
)
```

The `id` primary key is what makes the credits flow idempotent — both
the Stripe webhook and the gating layer construct deterministic ids so
a retried delivery or a double-clicked request can't double-spend.

## 6. End-to-end test

1. Set test-mode keys + the four price IDs above.
2. `stripe listen --forward-to http://localhost:3000/api/stripe/webhook`.
3. Sign in to the desktop app (test account).
4. Open **Billing → Credits → Buy credits**, pick `$5`, continue.
5. Use Stripe test card `4242 4242 4242 4242`, any future expiry, any CVC.
6. Confirm in this order:
   - Modal closes, "+500 credits added" toast appears.
   - Credit balance card refreshes to "$5.00".
   - `user_credits` table has a row with `balance = 500`.
   - `credit_transactions` table has a `purchase:<pi_...>` row with
     `delta = 500`.
7. Burn through the chat cap on a free account; the next request
   should succeed and `credit_transactions` should have a
   `consume:chat:<...>` row with `delta = -1`.
